## Requirements

**Build environment:**
- Java 21 (JDK)
- Maven 3.10+

**Testing:**
- JUnit 6.1.2
- JaCoCo 0.8.15 (code coverage reporting and verification)

## Build and test

```
mvn clean verify
```

Runs the tests, generates the JaCoCo coverage report (`target/site/jacoco/index.html`) and enforces a minimum of 80% line coverage.

## Usage

```java
import com.sportradar.worldcup.scoreboard.MatchSummary;
import com.sportradar.worldcup.scoreboard.Scoreboard;

import java.util.List;

Scoreboard scoreboard = new Scoreboard();

// Start a match (initial score: 0–0).
MatchSummary match = scoreboard.startMatch("Mexico", "Canada");

// Update the score.
scoreboard.updateScore(match.id(), 2, 1);

// Retrieve the current summary.
List<MatchSummary> summary = scoreboard.getSummary();

// Finish the match and retrieve its final result.
MatchSummary result = scoreboard.finishMatch(match.id());
```

## Assumptions

- The library is a standalone, in-memory component running within a single JVM. It does not provide persistence, external data provider integrations or event feed processing.
- A match is identified by a unique ID generated internally by the library, independently of team names.
- The same team may participate in multiple ongoing matches, and the same teams may meet in more than one match.
- Team names must not be null or blank. Leading and trailing whitespace is removed, while the original spelling and case are preserved. Home and away team names must differ, ignoring case.
- A match starts with the score 0-0. Negative scores are invalid. Score updates use absolute values rather than increments, allowing corrections (for example, after a VAR decision).
- Finishing a match removes it from the scoreboard. Any later operation on its ID, including a late score update, is rejected with `MatchNotFoundException`. Handling late or out-of-order events is the responsibility of the caller (e.g. a data provider layer).
- The summary contains only ongoing matches, ordered by total score descending and, for equal totals, by the most recently started match first.
- Public operations are thread-safe within a single JVM.

## Design decisions

- **API:** `startMatch`, `updateScore`, `finishMatch` and `getSummary`. Lifecycle operations return an immutable `MatchSummary` (`finishMatch` returns the final result); `getSummary` returns an immutable list. Internal `Match` objects are never exposed.
- **Domain model:** `Scoreboard`; the package-private immutable records `Match` and `Team` (validates and trims the name, compares names ignoring case); the public immutable records `MatchId` (wrapping a UUID generated by the library) and `MatchSummary` (team names as strings). No third-party runtime dependencies.
- **Storage:** the scoreboard keeps a private mutable `HashMap<MatchId, Match>` and replaces the immutable `Match` instance whenever its state changes. The map contains only ongoing matches; `finishMatch` removes the entry.
- **Ordering:** individual scores are `int`, the total used for ordering is `long`. Ties are broken by a monotonically increasing sequence number assigned in `startMatch` rather than by timestamps, which can collide. The sequence number is not exposed.
- **Concurrency:** all public `Scoreboard` operations are guarded by a single `synchronized` monitor, so every summary is a consistent snapshot.
- **Errors:** Unchecked exceptions derived from `ScoreboardException` are used for invalid team names, invalid scores and unknown match IDs (including IDs of finished matches). `NullPointerException` is used for null arguments.

## Build decisions

- Java 21 is the target version (`maven.compiler.release`).
- JUnit 6.1.2 is managed through `junit-bom`, and its built-in assertions are used.
- JaCoCo enforces the 80% line coverage threshold in the Maven `verify` phase.
- `Automatic-Module-Name` is set to `com.sportradar.worldcup`, giving a stable module name without a full `module-info.java`.
- No Maven Wrapper is included; the project uses an installed Maven distribution.

## Trade-offs

- `Automatic-Module-Name` instead of `module-info.java`: simpler and sufficient for a small library, but does not strongly encapsulate internal packages.
- An 80% line coverage threshold: encourages test coverage, but may fail the build when new code is added without tests.
- No Maven Wrapper: keeps the repository smaller, but contributors must install a compatible Maven version themselves.
- `HashMap` with on-demand sorting: updates and lookups stay simple and efficient (O(1) on average), but each summary requires sorting (O(n log n)).
- Immutable `Match` objects with a mutable internal map: domain objects are never mutated and the map is not copied on every update.
- A single synchronization monitor: simple and correct, but limits concurrent access compared with finer-grained locking.
- Finished matches are removed from the scoreboard: no memory growth and a simpler model (no lifecycle states), but an unknown match ID cannot be told apart from an already finished one, and corrections after the final whistle are not possible.
- A team may play several ongoing matches at once: the assignment does not forbid it and it keeps validation simple, but it does not reflect real-world rules.
